## 한 줄 요약

검색·피드·광고·쇼핑에 흩어진 사용자 행동을 한 시퀀스로 모아 학습한 사내 범용 추천 모델(VM)을 리트리버 4종 + 통합 랭커로 서빙하고, 대형 Foundation Model의 지식을 증류해 홈피드 CTR +20% 같은 성과를 낸 NAVER의 개발·운영기.

> 본문이 글이 아니라 **NAVER Engineering Day 10th 세션 영상(약 52분)** 이라, 아래 정리는 영상에 나온 슬라이드 흐름을 옮긴 것입니다. 발표자: 오혜지·배주현·김민규 (NAVER 네이버앱 서비스).

## 핵심 정리

### 1. 개발 배경과 목표

- 문제: 한 사용자의 하루가 홈피드(육아 글 클릭) → 검색('후쿠오카 날씨') → 클립(야구 하이라이트 시청) → 광고(유아용품 클릭) → 쇼핑(여행 가방 구매)처럼 지면을 넘나드는데, 각 지면 모델은 자기 로그만 학습해 **같은 사람을 지면마다 처음 보는 사람처럼** 추천한다.
- 반대편 극단인 전 지면 통합 FM(Foundation Model)은 크고 무거워 요청마다 실시간 호출이 어렵다.
- 목표: **FM으로 배우고 VM(Vertical Model)으로 서빙**한다. VM은 전 지면 액션을 한 사용자의 한 시퀀스로 모아 학습하고, FM의 지식을 Knowledge Distillation으로 받아 품질을 올린다. FM 하나로 여러 VM을 함께 개선하는 구조.
- KPI: 피드·뷰어 체류시간, 콘텐츠 노출·클릭, 광고 매출·노출·클릭, 그리고 광고와 콘텐츠를 같은 맥락에서 추천하는 것.
- AS-IS 지면별 로그로 따로 학습 → TO-BE 전 지면 로그로 함께 학습한 VM + FM KD.
- 적용 지면: 홈피드·클립뷰어·클립탭 (투데이피드·광고 소재는 실험 중).

### 2. VMs 시스템 구조

공통 데이터(User Sequence = 피드·클립·검색·광고·쇼핑의 전 지면 액션 시퀀스, User·Item Feature) → 학습 데이터 생성(액션 토크나이즈, 액션 bitmask 통합 시퀀스 가공, 학습셋 구성) → **1단계 리트리버 4종**(HSTU_DCAMS·AlphaRec·PLUM·HexaGraph, 각 최대 K개 후보) → 후보 병합 → **2단계 HSTU_DCAMS 통합 랭커** → 콘텐츠 지면(홈피드·클립탭 등) / 광고 지면(광고 소재).

| 리트리버 | 방식 | 강점 |
| --- | --- | --- |
| HSTU_DCAMS | 액션 시퀀스 기반 생성형 추천 | 소비 강도·행동 순서를 그대로 보존 |
| AlphaRec | LLM 텍스트 임베딩 + 협업 필터링 | 신규·콜드 아이템 zero-shot |
| PLUM | 시맨틱 ID(SID) 생성형 검색 | 임베딩 테이블 없이 코드 생성 |
| HexaGraph | 이종 그래프 + 대조 학습 | 콘텐츠 타입·작성자 관계 활용 |

### 3. 리트리버와 통합 랭커

**HSTU_DCAMS 리트리버** — 아이템 토큰(Φ = item ID ‖ 카테고리 ‖ 작성자, a = 액션 bitmask + SKIP·HIDE)을 HSTU(STU) 블록에 넣고, 단기·중기(스케일 풀링)·장기(누적 평균)·관심사 라우터(N개)로 나눈 D-CAMS 슬롯에서 `SlotMax = max_s cos(s_s, e_item)`로 top-K를 뽑는다.
- 3요소: ① action-aware 시퀀스(클릭만/끝까지 시청/SKIP을 다른 신호로), ② pointwise SiLU attention + relative attention bias(소비 강도 보존, 시간차 Δpos·Δt 반영), ③ multi-scale-interest 슬롯 + SlotMax(단기 0.21/중기 0.18/장기 0.25/관심사1 0.83/관심사N 0.30처럼 한 슬롯만 맞아도 후보로 올라옴).
- 한계: 학습된 아이템 ID만 추출할 수 있어 신규 아이템을 즉시 후보에 넣기 어렵다.

**AlphaRec** — 아이템 타워는 item_meta(제목·본문·캡션) → Qwen3-Embedding-8B(frozen) → MLP_A(학습) → LightGCN(warm만, 주기 갱신) → 아이템 벡터 → ANN 색인. 유저 타워는 IRA 자연어 프로필 → MLP_U → e_sem, 최근 이력의 단기/중기/장기 구간 평균 z_col을 결합해 `u_k = norm(z_col,k + e_sem)` → 구간별 HNSW 검색 → 라운드로빈 top-K.
- 3요소: zero-shot 추천(텍스트만 있으면 신규 아이템도 후보), 빠른 수렴(frozen 임베딩 위 MLP만 학습해 ID 랜덤 초기화 대비 좋은 초기값), 자연어 프로필 기반 사용자 표현(이력이 적은 사용자도 프로필로 추천).
- 한계: 텍스트 정보가 부족한 콘텐츠는 특성 파악이 어렵고, 이력을 평균으로 요약해 세밀한 행동 순서·맥락 반영에 한계.

**PLUM** — RQ-VAE로 콘텐츠 임베딩을 계층 코드(SID, c1·c2·c3…)로 양자화하고(`L = L_recon + L_vq + λ·L_con`, L_con은 함께 본 아이템을 가깝게 하는 InfoNCE), Transformer가 `[BOS] + 유저 맥락 + 이력 SID + 시간`을 받아 다음 아이템의 코드를 레벨별로 생성한 뒤 constrained beam search로 실제 존재하는 코드만 남겨 아이템으로 변환한다.
- 3요소: table-free 시맨틱 ID(아이템 임베딩 테이블 대신 데이터로 표현), coarse-to-fine 생성(큰 주제 → 세부), collaborative-aware SID(협업 시그널을 코드에 반영).
- 한계: 인기 아이템에 치우친 생성, 학습·서빙 단계가 여러 겹이라 복잡.

**HexaGraph** — 클립·포스트·블로그·카페·작성자를 한 이종 그래프로 묶고, 타입별 인코더 → 엣지 드롭으로 만든 두 뷰를 R-GCN(가중치 공유)에 통과시켜 `L_GCL`(같은 노드 가깝게) + triplet loss + 엣지 복원 loss로 학습. 사용자가 함께 본 콘텐츠를 시드로 이웃을 확장한다.
- 3요소: 이종 크로스도메인 그래프, 타입별 인코더 + R-GCN(관계마다 다른 가중치), 그래프 대조 학습(유저 노드 없이도 학습 가능).
- 한계: 소비 순서·최신성을 학습에 직접 반영하지 못한다.

**HSTU_DCAMS 통합 랭커** — 4개 리트리버 후보(각 ≤K)를 합쳐 중복 제거 후, 후보별 target attention으로 이력 h1..h10 중 어디에 주목할지 다시 계산하고(`u_s = Σ α_j(c)·h_j`), `max_s cos(u_s, c)`로 정렬해 상위 N개를 낸다. 학습은 listwise softmax(정답 다음 아이템 + 랜덤 네거티브).
- 3요소: candidate-aware D-CAMS 슬롯(후보마다 관심사 분해 — 단기 0.31/중기 0.28/장기 0.35/관심사1 0.82), 가벼운 후보 인코딩과 병렬 점수 계산(item ID 조회 하나), 같은 입력·분리된 학습(리트리버와 랭커를 독립적으로 학습·갱신).
- 한계: 후보를 아이템 ID로 표현하므로 미등록 신규 아이템은 모두 UNK 벡터가 되어 순위 구분이 어렵다.

### 4. 지면별 적용 현황과 성과 (콘텐츠 지면 ABT, Control 대비)

| 모델 | 홈피드 (CTR / 인당 클릭) | 클립뷰어 (재생수 / 재생시간) | 클립탭 (CTR / 인당 클릭) |
| --- | --- | --- | --- |
| VM 전체 | +20.0% / +20.6% | +2.0% / +2.8% | +7.3% / +25.6% |
| HSTU_DCAMS | +10.8% / +12.9% | -0.3% / 0.0% | +0.6% / +4.6% |
| AlphaRec | +2.2% / +3.6% | +0.5% / +0.3% | +2.5% / +2.8% |
| PLUM | +2.0% / +0.5% | +0.8% / +0.5% | 유의차 없음 |
| HexaGraph | +0.5% / +0.5% | 0.0% / +1.9% | +4.1% / +16.8% |
| HSTU_DCAMS 통합 랭커 | +3.4% / +2.1% | +1.0% / +0.1% | 유의차 없음 |

광고 소재 개인화 ABT(진행 중): 콘텐츠 지면에서 성과를 낸 리트리버를 광고 L1(candidate retrieval)으로 붙이고 L2 CTR/CVR 예측이 랭킹을 맡는 구조. 기존 ARA-P를 빼면 eCPM -3.1%·매출 -2.5%·CTR -4.1%인데, VM+heuristic 랭킹(CTR 가중치 A)으로 +5.5%·+6.1%·-1.9%·CPC +7.6%, 가중치 B로 +5.1%·+5.6%·-1.7%·+6.9%. eCPM·매출은 올랐지만 CTR은 아직 대조군보다 낮아, ARA-P를 뺄 때 잃는 CTR의 53~59%를 되찾은 단계. 다음 단계는 HSTU_DCAMS 랭킹 도입과 노출 소재 제외 로직.

### 5. 서빙과 최적화

- **공통 이력 조회**: DOT(사내 검색엔진) 역할인 배치가 인터랙션·카테고리·작성자를, Dexter(실시간 인터랙션 서비스)가 최신 이벤트를 담당. 같은 아이템·액션은 합치고 빠진 메타는 DOT에서 채워 HSTU·AlphaRec·HexaGraph가 함께 쓴다.
- **HSTU_DCAMS**: 추천 서버(CPU, arc-ras)가 시퀀스를 조립하고 HTTP zstd 압축으로 GPU 모델 서버(MLX)에 넘긴다. 모델 서버는 API 프로세스(uvicorn ×3)와 추론 프로세스를 ZMQ 큐로 분리.
- **AlphaRec**: 짧은 주기로 MLP를 처음부터 학습해 아이템 벡터를 만들고, ANN(HNSW) 색인은 블루-그린으로 통째로 교체. 요청 시에는 CPU에서 구간별 사용자 벡터 → 구간마다 병렬 검색 → 라운드로빈.
- **PLUM**: 이력 KV 캐시는 한 벌만 저장(PagedAttention)하고 beam별 생성 KV만 쌓으며, 같은 이력 캐시를 모든 beam이 한 번에 읽는 Cascade Attention으로 처리량을 올린다. 생성된 c1~c6을 서비스별 아이템으로 매핑(충돌 시 선택 규칙).
- **통합 랭커 튜닝 순서**: ① Profiling(큐 대기/전처리/추론/후처리로 나눠 CPU 병목과 커널 launch 사이 GPU 유휴 확인) ② CUDA Graph(커널 launch 묶어 재생, 배치 크기별 녹화·최대 후보 수 고정, 초과 요청은 일반 실행) ③ Dynamic Batching(배치 대기 시간으로 지연↔처리량 조절 — 광고는 짧게, 콘텐츠는 길게).
- 지면 성격 차이: 콘텐츠는 후보·트래픽이 많고 처리량 우선, 광고는 후보·트래픽이 적고 응답시간 목표가 엄격해 지연 우선.

### 6. FM 지식 전이 (Knowledge Distillation)

- 구도: FM(LYNX, 전 지면 데이터로 학습, 오프라인 배치 추론)이 (유저, 아이템) 클릭 점수 테이블을 적재 → HSTU·AlphaRec·PLUM·HexaGraph가 학습할 때 같은 테이블에서 pseudo-label을 뽑아 사용. FM 하나가 여러 VM에 지식을 나누고 비용도 분담.
- Co-distillation 대신 **external distillation**을 고른 이유: 신선도는 조금 손해지만 VM 학습·서빙 비용이 그대로이고, 한 번 추론해 여러 VM이 재사용할 수 있다.
- supervision 계약 P/C/T/V: Population(어떤 유저·세션), Candidate(어떤 후보 묶음), Time(이벤트·점수 생성 시각), Version(FM 버전). 이 네 기준이 고정돼야 점수를 어떤 단위로 묶고 비교할지 정해진다.
- HSTU 적용 예: 학습 시점 직전 30분 내 FM 세션만 join(이후는 미래 정보라 제외) → 같은 유저·같은 FM 버전끼리 grouping → 점수 값이 아니라 **순서**만 pseudo-label로 사용(버전마다 분포가 달라서). 보조 head를 따로 두고 `L_KD = KL(softmax(FM 순서/T) ‖ softmax(VM 점수/T))`, `L = L_main + w·L_KD`. 서빙에는 서빙 head만 쓰이므로 서빙 산출물은 변하지 않고, loss weight·gradient scale·적용 구간 세 가지로 KD가 주 과제를 방해하지 않게 조절. 효과는 FM 순서를 섞은 대조군과 비교해 따로 측정.

### 7. 향후 계획

- VM 개선과 FM 지식 전이를 같은 학습 루프 위에서 동시에 굴리는 방향.
- 랭커 개선 예(오프라인 검증 중): 학습 단위를 유저 이력에서 **세션**으로 바꿔 실제 노출된 아이템 중 클릭한 것을 맞히게 하고, 후보 표현에 아이템 ID와 **콘텐츠 임베딩을 함께** 넣어 vocab 밖 아이템에도 점수를 매길 수 있게 한다.
