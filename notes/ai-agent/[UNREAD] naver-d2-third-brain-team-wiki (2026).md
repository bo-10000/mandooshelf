## 한 줄 요약

에이전트가 팀 일을 못 맞히는 원인은 모델이 아니라 팀 지식이 어디에도 적혀 있지 않기 때문이라 보고, GitHub Wiki를 AI가 읽고 쓰는 공유 지식층(Third Brain)으로 만들어 스킬 4개·승인 절차·테스트셋까지 갖춰 운영한 반년 기록.

> 본문이 글이 아니라 **NAVER Engineering Day 10th 세션 영상(약 33분)** 이라, 아래 정리는 영상 슬라이드 흐름을 옮긴 것입니다. 발표자: 이권재·김보규 (NAVER 테크 플랫폼, Observability). 영상 속 알람·대화 장면은 실제 사례를 바탕으로 재구성한 가상 예시.

## 핵심 정리

### 1. 에이전트가 우리 팀 일을 못 했다

- PoC: 알람 발생 → AI가 로그·지표 조회 → 원인 분석. 스택트레이스에서 코드 위치와 커밋 작성자까지 추적했고 **단순한 케이스는 풀렸다**.
- 그러나 같은 알람에 에이전트는 "데이터 수정 API 203행에서 예외", "null 체크 PR 제안" 같은 답을 냈고, 팀이 아는 답은 "삭제된 데이터에 대한 요청이라 정상 범위이고 주간 정리 배치가 처리하며 담당자는 두 달 전 A에서 B로 바뀌었다"였다. **팀의 답은 코드에도, 로그에도, 어떤 문서에도 없었다.**
- 팀 지식은 사람 머릿속·이슈 코멘트·메신저·개인 메모 네 군데에 흩어져 있었다.

### 2. Third Brain이란

- 이름은 Meta의 글에서 차용: First brain(사람 머리, 빠르지만 잊고 나만 안다) / Second brain(개인 메모 도구, 나만 본다) / **Third brain(팀이 공유하고 에이전트가 읽고 쓰는 지식층)**.
- Meta의 4요소와 비교: workspace(팀 위키) 있음 / CLI·MCP(git, 이슈 트래커 CLI) 있음 / 에이전트 하네스(Claude Code) 있음 / **skills(마크다운으로 적은 워크플로우) 없음** — 여기가 우리가 채운 부분.
- 담을 것·링크로 남길 것·담지 않을 것:

- **어디에 있고 왜 그렇게 정했는지**
  - 링크로 남길 것: 코드
  - 담지 않을 것: 진행 상태, 일정
- **알람 원인과 대응**
  - 링크로 남길 것: 이슈 상세
  - 담지 않을 것: 현재 지표값
- **설정값과 이유·용어·제약**
  - 링크로 남길 것: 상세 절차 원문
  - 담지 않을 것: 그 밖에 자주 바뀌는 것

- 라우팅 인덱스: 영역 단위로 "무엇이 어디 있고, 원문엔 어떻게 가나".
- 판단 기준: 팀 단위로 반복 참조될 것 / 잘 안 바뀌는 것 / 확인한 것만 남긴다. 일회성 작업 기록·확정되지 않은 논의·추정은 남기지 않는다.
- 문서 유형은 팀 포맷이 있으면 그것을, 없으면 Diátaxis(how-to / reference / explanation — 한 문서에 한 유형만). PARA는 실행 상태 기준이라 상태가 바뀌면 문서를 옮겨야 해서 제외.

### 3. 어디에 적나요?

- 첫 시도는 Confluence Wiki + 임베딩 검색: 같은 프롬프트에도 매번 다른 문서가 나왔고, 매크로 태그까지 AI가 읽어야 했다.
- 후보 비교: Confluence Wiki(포맷 제각각·매크로) / GitHub Repo(깔끔하지만 읽기 환경이 아님) → **GitHub Wiki 선택**(마크다운 강제, 매크로 없음, 변경 이력, clone 한 번).
- 규모가 작을 때는 임베딩 검색보다 **git과 grep**이 맞았다: 문서 220장 규모에서 grep 1초 이내, pull 한 번이면 최신. 이유는 키워드가 곧 식별자(컴포넌트명·호스트명·설정 키)이고, 에이전트가 위키를 따라가며 읽는 쪽이 임베딩 검색보다 정확하다는 연구와도 같은 방향.

### 4. 문서는 누가 업데이트하나요?

- 문제: 지식이 드러나는 순간(알람 대응 끝, 이슈 클로즈, 리뷰 정정)과 문서를 여는 순간은 다르다. 하루 한 번 배치 요약은 노이즈였고, **각자의 에이전트에 스킬**을 쥐여 주는 쪽을 택했다.
- 구조는 스킬 4개 + git 저장소 하나: 세션 시작 hook → 진입 스킬(언제 부를지 정하는 원칙과 Red Flags 표) → init(저장소 연결, 처음 한 번) / search(읽기 전용 조회) / update(초안 → 승인 → push) → 저장소(라우팅 인덱스, 쓰기 컨벤션, 지식 페이지).
- superpowers(obra)에서 가져온 것 ① **진입 스킬**: 세션 시작 hook이 진입 스킬 본문을 주입하고 그 지시문이 세션 내내 행동을 규율한다(엔진은 hook이 아니라 지시문). 실행 스킬은 호출될 때만 로드하고, 컨텍스트 압축 뒤 재주입.
- 가져온 것 ② **Red Flags**: 에이전트가 일을 건너뛸 핑계를 표로 미리 막는다 — "이건 내가 아는 내용"→조직의 값은 바뀌었을 수 있으니 회차 먼저, "말로 물어보자"→초안을 만들어 diff로 묻기, "너무 사소하다"→직감이 아니라 기준 문서, "push 했다고 나왔으니 됐다"→원격을 다시 읽고 한 줄 보고.

### 5. AI가 쓴 걸 믿을 수 있나요?

- 초안은 스스로 만들고 반영은 승인 뒤에: ① 초안 ② 자체 점검 ③ diff로 묻기 → (승인) ④ push. 승인 전에는 commit도, git add도 하지 않는다(Human-in-the-Loop).
- 대화 예: 에이전트가 diff와 함께 "원인은 동기화 뷰 계정의 라이선스 회수였습니다… viewer-b는 fallback으로 적었습니다. 반영할까요?" → 사용자 "viewer-b는 fallback이 아니라 스테이징이에요" → 에이전트가 정정 → 승인 후 `storage-sync.sh push`.
- 세션이 여럿이어도 편집이 섞이지 않게 **git worktree**: 세션마다 worktree를 만들고 공유 clone은 fetch 전용. 충돌하면 rebase 1회, 실패한 worktree는 보존, 성공하면 정리.

### 6. 그래서 잘 동작하나요?

- 사용자는 묻고 알려주기만 한다: using-third-brain(세션 시작, hook 자동) / third-brain-search(팀 지식이 필요한 질문, 에이전트가 스스로) / third-brain-update(새 사실, 에이전트가 스스로) / third-brain-init(처음 한 번, 사람이 직접).
- 테스트셋 4종: **S**(팀 지식이 있어야 답할 수 있는 질문 → search 호출), **U**(원인·결정·설정값을 새로 알려주는 대화 → update 호출), **N**(일반 지식·자주 바뀌는 정보·시스템 이름만 있는 질문 → 호출 없음), **R**(팀 문서로 만든 질문 → 정답 일치, LLM-as-a-judge). "무조건 호출하는 스킬도 호출률은 100%"라 호출하지 않아야 정답인 세트가 필요했다.
- 기준 조건: Sonnet 5.5, medium, 단독 설치, 문서·스킬 둘 다 있음, hook 켬 → **search 호출 100%, 조회 정답률 100%, update 호출 95%, 오호출 10%** (5% 단위 반올림, 오차 ±10%p).
- 요소별 ablation:

- **문서 유무**(있음/없음): 결정적 — 문서가 없으면 Sonnet 5.5도 0%, 있으면 Haiku 5.5도 100%
- **스킬 유무**(있음/없음): 있음 100% vs 없음 60%(이슈·코드 뒤짐, 시간 3배)
- **모델**(Haiku 5.5 / Sonnet 5.5 / Opus 5.5): update 호출 65/95/100%, 오호출 5/10/15% — 좋은 모델일수록 둘 다 늘어남
- **추론 강도**(low/medium/high): update 90/95/95%, 오차 범위
- **설치 환경**(단독 / 스킬 7개·도구 130여 개와 함께): 95% vs 85%, 오차 범위
- **세션 시작 hook**(켬/끔): update 95% vs 70% — hook을 끄며 "확인되면 남기겠다"처럼 미루고 끝남

- 수치를 읽을 때 감안할 점: 짧은 고정 문장 세션만 측정했고(긴 작업 대화·개인 설정 환경은 측정 밖), 테스트셋이 스킬에 맞춰져 있어 과적합 위험이 있다.

### 7. 다시 첫 장면으로

- 같은 알람에 대해 이번에는 `third-brain-search`가 먼저 팀 지식을 확인하고, 원인·대응·담당자 변경까지 출처와 함께 답했다. 사용자가 "담당자가 B에서 C로 바뀌었다"고 하자 `third-brain-update`가 diff 초안을 만들어 승인 후 push.
- 결론: **"모델은 그대로다. 달라진 건 먼저 읽는 문서가 생긴 것이다."** 반년 동안 문서 220장, 커밋 800건 가까이. 지킬 절차는 하나도 늘지 않았다.
- 정리: 어디에 적나요(GitHub Wiki, git·grep) / 누가 업데이트하나요(진입 스킬, Red Flags) / 믿을 수 있나요(Human-in-the-Loop, git worktree) / 잘 동작하나요(문서·스킬·모델·hook, LLM-as-a-judge).
