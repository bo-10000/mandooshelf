## 한 줄 요약

컴포넌트는 이미 있는데 화면이 제각각이던 토스뱅크 **대출 심사 내부 툴**을, 상품×단계로 화면을 늘어놓는 구조 분해와 현업 담당자 업무 관찰(교차 검증)로 다시 이해하고, **화면 단위 공통 패턴 3가지**(리스트 화면 / 단계별 작업 화면 / 부가 정보 영역)로 패키지화한 과정. 핵심은 컴포넌트를 더 만드는 게 아니라 **"컴포넌트를 어떻게 조합·배치할지"의 기준**을 만들고, 그 기준을 문서·모듈로 팀에 심은 일이었다.

> 글: 신재희(Product Designer, 토스뱅크), 2026-11-25.

## 문제 — 같은 업무인데 버튼 위치가 상품마다 다르다

- 대출 심사 플랫폼은 대출 운영 담당자가 매일 쓰는 내부 업무 툴이다. 신청 건을 열어 정보·서류에 문제가 없는지, 다음 단계로 넘어가도 되는지 확인한다.
- 상품별 처리 흐름이 다른 건 자연스럽지만, **같은 목적의 행동까지 다르게** 만들어져 있었다.
  - '확정' 버튼이 주택담보대출은 화면 우측 하단, 전세자금대출은 좌측 안쪽에 있었다.
  - 단계별 주요 과업 버튼이 노출되는 방식도 상품마다 달랐다.
- 결과: 담당자가 팀을 옮기면 같은 업무를 다시 익혀야 하고, 적응·교육 비용이 팀에 남는다.
- 중요한 지점 — **디자인 시스템이 없던 게 아니다**. 버튼·테이블·필드 같은 기초 컴포넌트는 있었지만, 전담 디자이너 없이 각 팀 요청에 맞춰 빠르게 확장되면서 **화면을 어떻게 구성하고 배치할지의 공통 기준**이 없었다.

![대출 심사 툴 화면 — 상품마다 다른 구성](/mandooshelf/images/toss-design-system-loan-review-tool-2026/02-confirm-button.png)

## 1단계 — 고치기 전에 제품 구조부터 분해

- 제품에서 해야 할 작업을 체크리스트로 만들어 실제 환경에서 하나씩 따라 해 봤지만, 같은 작업도 상품마다 화면 구성·처리 방식이 달라 순서만으로는 흐름이 잡히지 않았다.
- 그래서 **상품별 화면을 단계별로 캡처해 한 아트보드에 나란히** 놓았다. 세로 = 상품, 가로 = 단계. 같은 단계끼리 비교하니 차이가 한눈에 보였다(예: 같은 확인 단계인데 어떤 상품은 모달, 어떤 상품은 화면 내 처리).
- 차이마다 PO·엔지니어에게 이유를 물어 **업무상 필요한 차이 / 만들어진 시점이 달라 생긴 차이**로 구분해 표로 정리했다. 이 구분표가 이후 공통 패턴을 뽑는 출발점이 됐다.

![상품(세로) × 단계(가로)로 화면을 늘어놓은 비교 아트보드](/mandooshelf/images/toss-design-system-loan-review-tool-2026/03-artboard.png)

## 2단계 — 사용자에게 직접 묻기: 업무는 순서대로 흐르지 않는다

- 제품을 써 보는 것만으로는 실제 업무 방식을 알기 어려워, UX 리서처와 함께 운영 담당자를 인터뷰하고 일하는 모습을 관찰했다.
- 예상: 정보 확인 → 서류 검토 → 확정의 순차 진행. 실제: **앞 단계로 돌아가 다시 확인**하고, **모니터 양쪽에 여러 화면을 띄워 교차 검증**하며 일한다.
- 설계에 반영된 변화: 순차 흐름은 기본 패턴으로 두되, 교차 검증용 화면은 **단계와 무관하게 언제든 조회**할 수 있어야 한다(특정 화면을 새 창으로 띄우는 장치 등).
- 팁: 고맥락 제품이면 **도메인을 익힌 뒤에 인터뷰**하라. 인터뷰어의 도메인 이해도가 들을 수 있는 이야기의 깊이를 바꾼다.

![운영 담당자 인터뷰에서 나온 이야기](/mandooshelf/images/toss-design-system-loan-review-tool-2026/04-interview.png)

## 3단계 — 컴포넌트가 아니라 화면 패턴을 정의

- 목표는 모든 상품을 똑같이 만드는 게 아니라 **반복되는 화면과 행동에 일관된 기준**을 세우는 것.
- 컴포넌트를 더 만드는 대신, 반복되는 화면을 세 가지 패턴으로 정의했다.
  - **리스트 화면**: 심사할 신청 건을 찾고 선택
  - **단계별 작업 화면**: 신청자 정보·서류 검토
  - **부가 정보 영역**: 교차 검증에 필요한 정보를 언제든 확인
- '확정' 같은 핵심 행동의 위치와 동작 방식까지 패턴에 포함하고, 제품 안에서 **패키지화**해 어느 상품에서든 가져다 쓸 수 있게 만들었다. 컴포넌트만으로 안 되는 부분은 새 구조로 보완.
- 효과: 새 상품 설계를 "빈 화면에서 고민"이 아니라 **패턴을 고르고 조합하는 일**에서 시작한다.
- 합의한 패턴·규칙은 문서로 모았다(이전엔 메신저와 여러 문서에 흩어져 같은 설명을 반복해야 했다). **DLOS Docs**를 AI로 만들어 규칙 질문을 문서 기준으로 시작하게 했다.

![정의한 세 가지 화면 패턴을 패키지화한 패턴 라이브러리](/mandooshelf/images/toss-design-system-loan-review-tool-2026/05-patterns.png)

![AI로 구축한 DLOS Docs — 패턴과 규칙을 한곳에서 확인하는 공통 문서](/mandooshelf/images/toss-design-system-loan-review-tool-2026/06-dlos-docs.png)

## 만드는 것보다 어려웠던 것 — 설득

- 좋은 패턴을 만들어도 바로 쓰이지 않는다. 상품이 빠르게 성장하는 시기라 디자인 시스템 적용은 우선순위가 아니었고, 각자 방식으로 운영하던 팀을 설득하는 과정이 길었다.
- 초기엔 "공통 구조를 써야 한다"고 말로 강조했지만, 반복해서 이야기하다 보니 PO·PM의 실제 걱정은 **속도**(기존 방식을 바꾸면 출시가 늦어질 수 있다)라는 걸 알게 됐다.
- 전환점: 그 우려에 공감하면서 **장기 비용**을 함께 계산. 각자 만들면 당장은 빠르지만 상품이 늘 때마다 같은 구조를 다시 만들고, 담당자가 바뀔 때마다 새 화면을 익혀야 한다. 공통 구조가 쌓이면 다음 상품은 더 적은 비용으로 만든다.
- 이후 흐름이 바뀌어 다른 상품팀이 먼저 "저희도 같은 걸로 쓸 수 있을까요?"라고 묻고, 기획 단계부터 플랫폼팀에 찾아오기 시작했다.
- 물론 전부 공통화할 수는 없다. **어디까지 공통화할지는 비즈니스 우선순위와 실제 기능을 보고 함께 정하는 것도 플랫폼의 몫**이라고 정리한다.

## 결과 — 같은 언어로 말하게 되다

- 직무와 무관하게 같은 기준으로 대화할 수 있게 됐고, 커뮤니케이션 비용이 눈에 띄게 줄었다. 같은 고민을 두세 번 반복하지 않는다.
- 예외는 팀 안에서 알아서 처리하던 방식에서 **공통의 자리에서 함께 논의**하는 방식으로 바뀌었다.
- 가장 실감한 순간: 한 상품 방식을 다른 상품에 그대로 적용해 달라는 요청에 **엔지니어가 디자이너보다 먼저** "이러면 예전처럼 상품마다 달라지지 않을까요?"라고 물었다.

## 적용해 보려면 (글의 세 가지 조언)

- **해결 전에 실제 사용을 보라** — 화면만 봐서는 문제를 못 잡는다. 어떤 순서로 쓰고, 어디서 다른 화면을 오가고, 어디서 막히는지 직접 봐야 한다.
- **컴포넌트 조합까지 정의하라** — 반복되는 화면 구조를 패턴·모듈로 만들면 매번 PO·PM·PD를 새로 설득하지 않아도 된다. 모듈은 기술 산출물이자 **팀 간 합의를 담는 기준**이다.
- **기준을 함께 관리할 방법을 정하라** — 예외가 생길 때 각 팀이 알아서 고치면 다시 갈라진다. 플랫폼팀과 함께 확장/신규 패턴을 정하고, **무엇을 왜 그렇게 정했는지**까지 문서로 남긴다.
