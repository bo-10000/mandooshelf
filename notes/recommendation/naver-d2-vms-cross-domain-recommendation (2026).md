## 한 줄 요약

지면마다 따로 학습하던 추천을, **피드·클립·검색·광고·쇼핑의 행동을 한 사용자의 한 시퀀스로 모아 학습한 VM(리트리버 4종 + 통합 랭커)** 으로 바꾸고 실시간 서빙까지 붙여 **홈피드 CTR +20.0%** 같은 성과를 냈다. 초거대 FM(LYNX)의 지식을 VM에 증류하는 **KD는 이 위에 얹는 별도 확장 트랙**이다.

> 글ではなく **NAVER Engineering Day 10th 세션 영상(약 52분)** 정리본. 발표: 오혜지·배주현·김민규 (NAVER 네이버앱 서비스).

## 큰 그림

- **기존(AS-IS)**
  - 학습 데이터: 지면별 로그만 (홈피드 모델은 홈피드 로그만)
  - 실시간 서빙: 가능
  - 이번 발표에서의 위치: 같은 사람을 지면마다 처음 보는 사람처럼 대함
- **FM(LYNX)**
  - 학습 데이터: 전 지면 데이터로 학습한 초거대 모델
  - 실시간 서빙: **불가** — 무거워서 오프라인 배치 추론만
  - 이번 발표에서의 위치: 답안지(클릭 점수)를 미리 만들어 두는 역할
- **VM(Vertical Model)**
  - 학습 데이터: **똑같이 전 지면 유저 행동 시퀀스**를 학습
  - 실시간 서빙: **가능** — 경량화하고 리트리버 4종·통합 랭커로 쪼갬
  - 이번 발표에서의 위치: **발표의 본체. 위 +20% 성과는 여기서 나온다**
- **FM KD(지식 전이)**
  - 학습 데이터: FM이 매긴 점수를 VM 학습에 증류
  - 실시간 서빙: VM 서빙은 그대로
  - 이번 발표에서의 위치: 위에 얹는 확장 트랙, 효과는 대조군으로 따로 측정 중

- 기존과 VM의 차이는 "지면별 모델이냐"가 아니라 **무엇을 먹고 학습했느냐**다. VM은 홈피드·클립뷰어·클립탭이 **같은 파이프라인(리트리버 4종 + 통합 랭커)을 함께 쓰고**, 배포·튜닝만 지면 성격에 맞게 조정한다.
- 개발 배경: 한 사용자의 하루가 홈피드(육아 글 클릭) → 검색('후쿠오카 날씨') → 클립(야구 하이라이트) → 광고(유아용품) → 쇼핑(여행 가방)처럼 지면을 넘나드는데, 지면별 로그만 보면 다른 지면에서 드러난 관심사를 쓰지 못한다.
- 목표: **FM으로 배우고, VM으로 여러 지면에 서빙한다.** KPI는 체류시간·노출·클릭, 광고 매출, 그리고 광고와 콘텐츠를 같은 맥락에서 추천하는 것.

## 시스템 구조 (한눈에)

공통 데이터(전 지면 액션 시퀀스 + 유저·아이템 피처) → 학습 데이터 생성(액션 토크나이즈·bitmask 통합 시퀀스) → **1단계 리트리버 4종**(각 최대 K개 후보) → 후보 병합·중복 제거 → **2단계 통합 랭커** → 콘텐츠 지면(홈피드·클립탭 등) / 광고 지면(광고 소재 추천).

## 리트리버 4종 + 통합 랭커 (역할과 논문)

내부 수식은 빼고 **무엇을 하는지 한 줄 + 기반 논문**만 남긴다. 실제 인퍼런스가 어떻게 갈리는지는 바로 다음 절에서 따로 본다.

- **HSTU_DCAMS** (리트리버)
  - 역할: 유저의 액션 시퀀스(클릭만 / 끝까지 시청 / SKIP)를 그대로 먹고 다음에 볼 아이템 후보를 뽑는다. 소비 강도와 행동 순서를 보존하는 게 강점
  - 기반 논문: *Actions Speak Louder than Words: Trillion-Parameter Sequential Transducers for Generative Recommendations* (2024)
- **AlphaRec** (리트리버)
  - 역할: 제목·본문 같은 텍스트를 LLM 임베딩으로 읽어 **신규(콜드) 아이템도 바로** 후보에 올린다. 이력이 적은 유저는 자연어 프로필로 보완
  - 기반 논문: *Language Representations Can Be What Recommenders Need* (2025), *IRA: Adaptive Interest-aware Representation and Alignment for Personalized Multi-interest Retrieval* (2025), *Dual-Intext Space Representation Optimization for Recommendation* (2026)
- **PLUM** (리트리버)
  - 역할: 아이템을 계층적 시맨틱 ID(코드)로 표현하고, 그 코드를 생성해 후보를 찾는다. 큰 주제 코드부터 좁혀 가는 생성형 검색
  - 기반 논문: *Recommender Systems with Generative Retrieval* (2023), *PLUM: Adapting Pre-trained Language Models for Industrial-scale Generative Recommendations* (2025)
- **HexaGraph** (리트리버)
  - 역할: 클립·포스트·블로그·카페·작성자를 한 이종 그래프로 묶어, 함께 본 이웃으로 후보를 확장한다
  - 기반 논문: *RankGraph: Unified Heterogeneous Graph Learning for Cross-Domain Recommendation* (2025)
- **HSTU_DCAMS 통합 랭커**
  - 역할: 4종 후보를 한 번에 점수 매겨 최종 순서를 정한다. 후보마다 유저 이력 중 어디에 주목할지 다시 계산하는 2단계 랭커
  - 기반 논문: 같은 HSTU 계열 (위 2024 논문)
- **FM KD**
  - 역할: FM이 매긴 클릭 점수의 **순서**를 VM 학습에 보조 신호로 증류한다 (아래 지식 전이 절)
  - 기반 논문: *ExFM* (2025)

- 왜 4종을 같이 쓰나: 잘하는 게 서로 달라서다(행동 순서 / 텍스트·콜드스타트 / 코드 생성 / 그래프 관계). 후보를 합친 뒤 랭커가 고르고, 각자의 약점(신규 아이템·행동 순서·인기 편향 등)을 서로 메운다.

## 인퍼런스 방식: 4종이 다 돌지만, 4종 다 무거운 GPU 추론은 아니다

- 요청이 들어오면 **4종 리트리버가 모두 실행된다.** 각자 후보를 만들고, 합쳐서 중복을 지운 뒤 랭커가 고르는 구조라 하나라도 빠지면 후보 풀이 달라진다. (광고 실험은 그중 HSTU_DCAMS·AlphaRec 2종만 붙였다.)
- 다만 **4개 모두가 무거운 실시간 GPU 추론을 도는 건 아니다.** 실시간으로 계산하는 것과, 미리 계산해 둔 것을 찾아오는 것이 섞여 있다.
- **HSTU_DCAMS — 실시간 GPU 모델 서버 추론**
  - 무거운 추론만 GPU 서버로 떼어내고, 요청 본문을 압축해 보낸다.
- **PLUM — 실시간 GPU 생성**
  - 이력 KV 캐시를 한 번 계산하고, 이후 Beam Search들이 그 캐시를 함께 읽어 쓴다.
- **AlphaRec — 실시간 GPU 추론 없음**
  - 아이템 벡터는 주기 학습 후 ANN 색인으로 미리 구워 두고, 새 색인은 블루-그린으로 통째 교체한다.
  - 요청 시엔 **CPU에서 유저 벡터만 만들고 ANN 검색만** 실행한다.
- **HexaGraph — 실시간 모델 추론 없음**
  - 미리 계산해 둔 이웃 목록을 사내 검색엔진(DOT)에서 **조회만** 한다.
- 정리하면 실시간 GPU를 쓰는 건 HSTU_DCAMS와 PLUM, AlphaRec과 HexaGraph는 "미리 만들어 둔 것(색인·이웃 목록)을 요청 때 찾아오는" 쪽이다. 그래서 4종을 다 돌려도 지연과 비용을 감당할 수 있다.

## 통합 랭커는 어떻게 후보를 고르나 (동작과 한계)

**동작**

- 유저 이력을 HSTU 인코더로 **한 번만** 인코딩한다. 후보마다 이력을 다시 읽지 않는다.
- 그다음 합쳐진 후보를 **하나하나마다 Target Attention**을 적용한다. "이 후보를 평가할 때 유저 이력 중 어디에 집중할지"를 후보마다 다르게 계산하는 것.
- 이렇게 나온 슬롯별 점수로 최종 순위를 매긴다.
- 후보끼리 서로 비교하는 계산은 하지 않고 **후보별 독립·병렬 계산**으로 속도를 확보한다.

**한계**

- 후보 표현에 **가벼운 아이템 ID 임베딩만** 쓴다. 그래서 학습 때 등록되지 않은 신규 아이템은 전부 **같은 UNK 하나로 취급**되어, 신규 아이템끼리 구분이 되지 않는다.
- 개선 예정: 아이템 ID에 **콘텐츠 임베딩을 더해** 학습 때 못 본 아이템에도 점수를 줄 수 있게 한다(아래 향후 계획).

## 랭커는 어떻게 학습했나 (End-to-End가 아니다)

- 리트리버 4종과 랭커를 **End-to-End로 묶어 학습하지 않는다.** 완전히 분리해서 각자 독립적으로 학습·갱신한다.
- 둘이 공유하는 건 **전 지면 액션 시퀀스 입력 포맷** 하나다. 랭커는 리트리버가 뽑아 준 후보에 의존하지 않고 **처음부터 자기 데이터로** 학습한다.
- **현재 학습 방식**: 유저 이력 다음에 올 아이템 1개를 맞히고, 오답은 **카탈로그에서 랜덤**으로 뽑는다. 리트리버와 비슷한 형태의 다음 아이템 예측이다.
- 이 방식의 약점: 실제로 같이 노출된 비슷한 후보들 중에서 1등을 가려내는 힘은 약하다. 랜덤 오답은 너무 쉽기 때문.
- **향후 개선**: 랜덤 오답 대신 **실제 세션에 노출된 후보 묶음 중 클릭한 아이템**을 맞히는 **세션 단위 학습**으로 고도화 중이다. "랭커를 랭커답게" 만드는 작업.

## 성과: 서비스 적용 vs 실험 중

ABT(Control 대비). **+20%대 수치는 FM 증류가 아니라 "전 지면 시퀀스로 학습한 VM을 구축·서빙한" 성과**다.

**실제 서비스 적용(채택)**

- **홈피드**: CTR **+20.0%**, 인당 클릭 **+20.6%**
- **클립뷰어**: 재생수 **+2.0%**, 재생시간 **+2.8%**
- **클립탭**: CTR **+7.3%**, 인당 클릭 **+25.6%**

**실험 진행 중**

- **투데이피드**: 실험 단계.
- **광고 소재 개인화**: 콘텐츠 지면에서 성과를 낸 리트리버를 광고 L1(후보 생성)으로 붙이고, 랭킹은 기존 광고 CTR/CVR 모델이 맡는 구조. VM + heuristic 랭킹으로 **eCPM +5.5%·매출 +6.1%**까지 올렸지만 **CTR은 기존 대비 -1.7%~-1.9%**로 아직 낮아 개선 중(기존 광고 개인화 리트리버 ARA-P를 뺄 때 잃는 CTR의 53~59%를 되찾은 단계). 다음은 HSTU 랭킹 도입과 노출 소재 제외 로직.
- **FM KD(지식 전이)**: 슬라이드에 구체적 수치가 없다. **FM 순서를 섞은 대조군과 비교해** 효과를 따로 측정 중.

- 참고: 리트리버·랭커별 기여도도 지면별로 따로 쟀다(예: HSTU_DCAMS 홈피드 CTR +10.8%, HexaGraph 클립탭 인당 클릭 +16.8%).

## 서빙 최적화 (수식 없이 핵심만)

- **공통 이력 조회**: 배치(DOT, 사내 검색엔진)로 과거 인터랙션·카테고리·작성자를, 실시간 서비스(Dexter)로 최신 이벤트를 받아 합친다. 모든 모델이 같은 유저 이력을 쓴다.
- **모델별로 다른 전략**: 위 "인퍼런스 방식" 절 참고 — 실시간 GPU 추론(HSTU_DCAMS·PLUM)과 미리 계산 후 조회(AlphaRec·HexaGraph)를 섞어 지연과 비용을 맞춘다.
- **랭커 GPU 튜닝 3단계**: ① 프로파일링으로 CPU 병목과 GPU 유휴 구간 찾기 → ② CUDA Graph로 작은 커널 실행을 묶어 재생 → ③ Dynamic Batching으로 배치 대기 시간 조절.
- **지면 성격이 튜닝을 가른다**: 콘텐츠 지면은 후보·트래픽이 많아 **처리량 우선**(대기 길게), 광고 지면은 후보·트래픽이 적고 응답시간이 빡빡해 **지연 우선**(대기 짧게).

## FM 지식 전이 (KD) — 확장 트랙

- 구도: FM(LYNX)이 오프라인으로 (유저, 아이템) 클릭 점수 테이블을 만들어 두면, VM 4종이 학습할 때 같은 테이블에서 **pseudo-label**을 뽑아 쓴다. FM 하나가 여러 VM에 지식을 나누고 유지 비용도 분담한다.
- **external distillation**을 고른 이유: 신선도는 조금 손해지만 VM 학습·서빙 비용이 그대로이고, 한 번 추론한 FM 점수를 여러 VM이 재사용할 수 있다.
- 적용 방식: 점수 값은 FM 버전마다 분포가 달라 그대로 쓰지 않고 **같은 유저·같은 FM 버전 안의 "순서"만** 라벨로 쓴다. VM에는 학습 전용 보조 head를 두어 실제 클릭을 맞히는 주 과제를 방해하지 않게 한다(서빙 산출물은 그대로).
- 검증: FM 순서를 준 경우 vs **FM 순서를 섞은 대조군**으로 효과를 분리해 측정.

## 향후 계획

- VM 개선과 FM KD를 같은 학습 루프 위에서 함께 굴리기. (E2E가 아니라 리트리버·랭커 각자 독립 학습이라는 구조는 유지)
- 랭커를 "랭커답게": 학습 단위를 유저 이력 → **세션**으로 바꿔, 그 세션에 실제 노출된 후보 중 클릭한 것을 맞히게 한다.
- 후보를 아이템 ID + **콘텐츠 임베딩**으로 함께 표현해, 학습 때 못 본 신규 아이템에도 점수를 줄 수 있게 한다.
- 광고 소재 개인화는 CTR 회복이 남은 과제(HSTU 랭킹 도입, 노출 소재 제외 로직). 모두 오프라인 검증 중.
