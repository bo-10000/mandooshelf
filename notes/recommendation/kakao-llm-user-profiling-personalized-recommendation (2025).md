## 한 줄 요약

약 100명의 카카오 전사 데이터 조직이 행동·위치·서비스 이용을 **'관심사 taxonomy + persona'라는 재사용 가능한 프로파일**로 바꾸고, 그 하나의 프로파일을 이모티콘·오픈채팅·쇼츠·다음/카카오·카나나 선톡 **다섯 추천 제품의 공통 파이프라인**에 연결한 이야기. 거대 모델 하나가 아니라 **프로파일을 만들어 여러 제품이 나눠 쓰는 포트폴리오** 접근이다.

> **출처 한계**: 30분 발표 영상의 **챕터별 요약본**(piletech)만 확인했다. 발표에 정량 성과가 있더라도 이 요약에는 담겨 있지 않아, 아래에 성과 수치는 없다.

## 문제 배경

- 카카오는 추천 제품이 여러 개인데, 각 제품이 사용자를 따로 이해하고 있었다. 필요한 데이터도 제품마다 달랐다(행동 로그, 위치, 서비스 이용, 대화).
- rule·ML·LLM을 하나로 통일하지 않고 **문제 성격에 따라 섞어 쓰는 것**을 전제로, 그 위에 공통으로 쓸 사용자 프로파일 계층을 두는 구도.
- 조직은 데이터 엔지니어·분석가·모델러·개발자·기획자 약 100명이 로그 수집부터 법률 검토·서빙까지 함께 맡는다.

## 큰 구도: 프로파일 하나 → 다섯 제품

1. **UFO (프로파일링)**: 행동 item을 **6개 축·730개 카테고리 taxonomy**로 태깅하고, **time-decay count**로 사용자별 관심 점수를 만든다. 여기에 성·연령 분류와 위치 모델(생활권·방문 목적·혼잡도)을 결합한다.
2. **persona 생성**: 구조화된 결과와 행동 로그를 LLM에 넣어 **persona와 그 이유를 텍스트로** 만든다. 대화 발화에서는 직접 추론과 간접 추론을 구분해 관심사를 보완한다.
3. **다섯 제품 공통 파이프라인**: 이모티콘·오픈채팅·쇼츠·다음/카카오·카나나 관심사 선톡을 모두 `candidate generation → ranking → post-processing → serving` 흐름으로 운영한다. 개인화 정보가 충분하면 **user-level**, 부족하면 **segment**, 그것도 없으면 **default**로 단계적으로 fallback한다.
4. **운영 품질을 제품의 일부로**: 모니터링, peer review, **privacy risk review**, 그리고 이해할 수 있는 대시보드·문서까지 요구사항에 넣었다.

## 무엇이 기반이고 무엇이 contribution인가 (UFO vs LLM)

- **UFO는 룰·전통 ML 집계**다. 730개 category 태깅, time-decay 점수, 성·연령 분류, 위치 모델까지 LLM 없이 만든다.
- **UFO의 1차 용도는 전사 공통 프로파일 1층**이다. 기존 추천 파이프라인의 피처·타게팅 입력으로 쓰인다. 기술적 신기함보다는 전사 데이터를 한곳에 모아 표준 프로파일을 깔아 둔 **엔지니어링 기반**에 가깝다.
- **주 contribution은 그 위에 얹은 LLM 페르소나 + 카나나 선톡**이다. 발표 제목(`LLM을 활용한 유저 프로파일링과 개인화 추천`)과 무게중심이 이쪽이다.
- 특히 상호작용 로그가 없는 콜드스타트에서 LLM으로 검색어·멘트를 만들고, 또 다른 LLM judge로 최신성·민감성까지 걸러 **먼저 말을 거는** 파이프라인이 핵심 시도다.
- 정리하면 "기존 ML 피처용 UFO를 그대로 두고, 그 위에 LLM 페르소나를 얹어 다섯 제품이 함께 쓰게 묶었다"가 발표의 주장이다.

## 추론 비용: 매 요청마다 LLM을 태우지 않는다

- **일반 추천 서빙(이모티콘·오픈채팅·쇼츠·다음)은 요청마다 LLM을 호출하지 않는다.** 미리 저장해 둔 프로파일을 꺼내 쓰는 기존 `후보 생성 → 랭킹 → 서빙` 구조다.
- **LLM 페르소나 생성도 실시간 추천이 아니다.** 프로파일 생성 단계에서 **배치·비동기로 만들어 저장**해 두고, 서빙은 저장된 결과를 읽는다.
- 다만 발표자가 "How보다 What을 소개한다"고 해서, **전체 유저 중 어느 범위까지 어떤 주기로 배치를 돌리는지는 요약본에 없다**(비용·규모 디테일 미기재).
- 다만 user-level persona를 만들려면 대상 유저 수만큼은 LLM을 한 번씩 태워야 하므로, 발표의 `user-level → segment → default` fallback 구조상 **로그가 충분한 활성 유저 위주로만 user-level을 생성하고 나머지는 세그먼트로 묶었을 여지**가 있다. (추론이며 발표 확인 내용은 아니다.)

## 카나나 관심사 선톡 — 하나의 흐름, 4단계 운영 파이프라인

발표 챕터가 앞뒤로 나뉘어 정리본에서 `케이스 1 / 케이스 2`로 갈라져 있었지만, **별개 서비스가 아니라 카나나 관심사 선톡 하나의 흐름**이다. 앞단은 컨셉과 생성, 뒷단은 실제 운영 파이프라인이다.

### 앞단 — 왜 먼저 말을 거는가, 무엇을 만들 것인가

- 추천에 필요한 아이템·상호작용이 없는 **콜드스타트**에서, 이미 있는 프로파일로 관심 있을 검색어·뉴스를 만들어 **먼저 말을 건다**. message와 quick response까지 생성.
- 사용자가 대화에 응할수록 프로파일이 다시 개선되는 **flywheel** 구조를 노린다.
- 개인정보를 지나치게 드러내면 광고처럼 느껴지므로 **표현의 구체성에 제한**을 둔다.

### 뒷단 — 보낼 거리를 고르고 보내는 4단계

1. **① 검색어·메시지 생성**: LLM이 **유저 프로파일을 직접 입력으로** 받아 검색어와 멘트를 만든다.
2. **② 필터링**: 별도 LLM과 rule이 **최신성 부족·브랜드 언급·멀티 토픽·민감 내용**을 걸러 중복을 제거한다. 사람 평가와 더 강한 LLM judge를 정렬시켜 필터 품질을 맞춘다.
3. **③ 검색**: 후보는 **BM25 + Sentence-BERT**, 두 결과를 **RRF(Reciprocal Rank Fusion)** 로 합친다.
4. **④ 발송 시간 최적화**: 피드백이 적은 상황이라 요일·시간대의 보상을 **contextual UCB**로 추정하고, 횟수·간격 제약 안에서 **linear programming**으로 최적 조합을 고른다.

- 이 4단계 중 **유저 프로파일이 직접 입력으로 들어가는 단계는 ① 생성 단계**임이 요약본에서 확인된다.
- ②는 ①이 만든 검색어를, ③은 걸러진 검색어를, ④는 발송 로그를 다루는 후속 단계다.
- ④의 `contextual UCB`에 시간대·유저 문맥이 들어가긴 하지만, **그 문맥 피처에 UFO 프로파일 속성이 포함되는지는 요약본에 명시되지 않아 미확인**이다.
