## 한 줄 요약

목적마다·상품마다 하나씩 늘던 트리 모델을 **PLE 기반 멀티태스크 모델(MTL) 하나로 합쳐**, 마케팅 타겟팅(AP 상대 +54%, 불필요 발송 -35%)과 상품 예측(MAE -66~79%, AUC +10%) 두 곳에서 **모델 수를 줄이면서 성과까지 올린** 토스 ML 챕터의 사례. 지난 TASTE 글은 여러 행동으로 **공유 표현을 만들어 다른 모델에 넘기는** 쪽이었고, 이번 글은 여러 과제의 **예측값 자체를 한 모델로** 내는 쪽이다.

> 글: 토스 ML 챕터, 2026-11-23.

## 문제 배경 — 모델이 수백 개가 되면

- 과제 하나에 트리 모델 하나는 처음엔 가장 단순하고 잘 돈다. 문제는 수십~수백 개가 된 뒤다.
- 비용이 **과제 수 × 상품 수**만큼 늘어난다. 모델마다 데이터 준비·학습·배포·모니터링 파이프라인이 따로 있고, 장애 지점도 그만큼 많다.
- 재학습 부담: 수백 개를 자주 다시 학습하기 어려워 한 번 만든 모델이 오래 고정된다. 새 데이터·새 실험도 모델마다 따로 돌려야 해서 개선이 밀린다.
- 데이터가 적은 과제(드문 행동·희소 정답 상품)는 따로 학습하면 배울 게 부족하고, **신상품은 개별 모델을 만들기 전까지 쓸 모델이 없다**.

## 공통 설계 (두 사례가 같은 뼈대)

- **공유 인코더**: 입력을 요약하는 부분은 과제와 무관하니 한 번만 계산해 모든 과제가 함께 쓴다.
- **PLE (Progressive Layered Extraction, Tencent, RecSys 2020)**: 공유 전문가 + 과제별 전문가를 두고, 과제별 게이트가 "어느 전문가를 얼마나 쓸지"를 정한다. 게이트가 공유 전문가와 자기 전문가만 보므로 다른 과제 간섭을 줄인다.
- **과제별 출력층 + 과제별 Loss 합산.** 샘플 안에서 **정답이 없는 과제는 그 과제 Loss만 빼고** 샘플은 유지한다(예: 앞 분류가 '아니오'면 뒤 수치 과제 정답 없음 → 샘플을 버리면 분류의 '아니오'를 못 배움).
- **Loss 균형**: 단위·분포가 다른 수치 과제는 타깃 표준화, 희소 양성 분류 과제는 양성 가중치(상한 있음).
- 이 뼈대 덕에 **데이터 적은 과제가 큰 과제에서 배우고**(공유 인코더·공유 전문가가 모든 과제 데이터로 학습), 트리로는 펴서 넣어야 했던 **시퀀스·묶음 입력을 모양대로** 읽을 수 있다.
- 사내 ML 플랫폼 위에서 데이터 준비 → 학습 → 예측 → 평가가 돌고, **매일 재학습**한다.

## 사례 1 — 유저 금융 행동 수십 개를 한 모델로 (분류만)

- 기존: 마케팅 목적이 생길 때마다 행동 예측 트리 모델 1개 추가 → 모델 수·운영비 계속 증가.
- 구조: 최근 행동 기록(시간 순 그대로) 요약 + 유저 프로필 요약을 섞고 → 공유 전문가 + 행동별 전문가 → 수십 개 행동 확률을 한 번에. **입력은 동의 기반 정보만**.
- 드문 행동은 흔한 행동에서 배운다. 행동별 전용 전문가는 1개뿐이고 나머지 표현은 모든 행동이 공유한다.
- 오프라인 (목적별 트리 모델 대비, 공통 비교 가능한 행동 기준)
  - Average Precision **약 54% 개선(상대값)**
  - 상위 N명 Recall **약 20% 개선**
  - AUC-ROC 거의 동일(소폭 개선) — 실제로 쓰는 건 "상위 N명"이라 상위권 정밀도 상승이 핵심이었다
- 온라인 (A/B, 두 상품군 모두 p < 0.001로 유의)
  - 상품군1: 기존 세그먼트 대비 **불필요한 발송 약 35% 감소**, 발송 대비 효율 약 **2배**
  - 상품군2: 클릭률 약 **1.7배**, 최종 전환율 **수 배**
- 이 결과 이후 마케팅 타겟팅에서 널리 활용 중(서비스 적용).

## 사례 2 — 상품마다 세 과제를 한 모델로 (분류 + 회귀 혼합)

- 기존: 상품마다 성격이 다른 3과제 → 과제 × 상품으로 트리 모델 **수백 개**. 신상품이 나오면 MLE가 그 상품 모델을 새로 학습해야 했고(개발 초기보다 상품 3배 이상 증가), 그대로 갔으면 모델 수가 몇 배 더 늘었을 상황.
- 구조 4단계
  - 유저 정보는 한 번, 상품 정보는 상품마다 요약
  - 두 요약을 맞붙여 "이 유저 × 이 상품" 표현 생성
  - 전문가 3종: 공유 전문가 · 과제별 전문가 · **상품 종류별 전문가**(비슷한 상품끼리 학습 공유)
  - 출력 3개: 앞 과제를 먼저 예측하고, 뒤 과제는 그 결과를 조건으로 참고(정답이 있는 경우에만 Loss)
- **중요한 신호를 실제로 쓰게 만든 설계** — 단순히 넣기만 하면 깊은 층에서 희석됐다
  - 핵심 신호는 출력층 가까이에 **전용 경로**로 한 번 더 투입
  - 이전 시점 정보와 현재 맥락을 **나란히** 주어 무엇이 바뀌었는지 모델이 직접 비교
  - 트리 모델은 같은 피처를 넣어도 신호를 어떻게 쓸지 분기 생성 과정에 맡기지만, 딥러닝 MTL은 이를 구조로 정할 수 있었다 — 성능 개선에 실제로 기여한 변경
- 얻은 것: 파이프라인 하나·재학습 한 번 / **신상품도 새 모델 없이** 상품 정보로 예측하고 학습에 쌓이면 반영 / 희소 정답 상품은 상품 종류별 전문가로 비슷한 상품에서 학습 / 앞 과제 결과를 조건으로 세 결과가 서로 맞물림
- 결과 (두 모델 모두 예측한 동일 유저·상품만 모아 같은 실제 결과로 채점)
  - 수치 과제 ① MAE **약 79% 감소**, ② MAE **약 66% 감소**
  - 분류 성격 과제 AUC **약 10% 향상(상대값)**
- 사례 2는 글에 **온라인 A/B 결과가 없다** — 오프라인 비교까지가 제시된 성과다.

## MTL이 어려운 점 (글에서 밝힌 것)

- **Negative transfer / 시소**: 공유층을 거치면 한 과제의 변경이 다른 과제를 해친다. PLE를 둘 다에 쓴 이유가 이 간섭 완화.
- **Loss 크기·형태 차이**: 그대로 더하면 한 과제가 학습을 독점. 수치 타깃 표준화 + **과제마다 Loss 형태도 분포에 맞게** 선택.
- **데이터 많은 과제가 드문 과제를 덮음**: 사례1은 양성 비율 가중치, 사례2는 상품 종류별 전문가로 대응.
- **모든 변경을 모든 과제에서 검증**: 작은 변경도 전 과제 지표를 다시 봐야 해서, 두 모델 모두 매일 서빙 예측을 실제 결과로 과제별 자동 채점해 변경 전후를 비교.
- **배포가 묶인다**: 재학습·배포는 한 번이라 편하지만, 한 과제만 따로 고치거나 되돌리기 어렵다.

## 참고 논문·선행 사례

- PLE — *Progressive Layered Extraction* (RecSys 2020, Tencent)
- Meta Lattice — Luo et al., KDD 2026 (arXiv:2512.09200): 광고 추천에서 수천 개 도메인×목적 모델을 비슷한 조합끼리 묶어 소수로 재설계, 품질 지표 상승 + 인프라 용량 약 20% 절감. "무엇끼리 묶을지"가 핵심이라는 점도 함께 강조.
- 같은 팀의 이전 글: TASTE, 토스의 추천 파운데이션 플랫폼 (`notes/recommendation/toss-taste-recommendation-foundation-platform (2026).md`)

## 합치기 전에 챙길 것 / 합친 뒤 얻는 것

- 합치기 전: **무엇끼리 묶을지**부터 정한다(같은 유저의 특정 행동끼리, 같은 상품의 세 과제끼리). **과제별 평가 기준**을 먼저 정해 통합 모델을 과제별로 확인한다 — 전체 평균이 좋아져도 일부 과제는 나빠질 수 있다.
- 합친 뒤: 운영이 가벼워지고(재학습·평가·개선을 한 곳에서 자주) 새 데이터·실험이 모델 하나에 반영된다. **새 과제·상품이 계속 생기는 조직일수록 효과가 크다.**
- 단, 모든 문제를 하나로 풀 수는 없고 토스도 문제에 따라 다른 모델을 함께 쓴다.
